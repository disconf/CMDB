# 组织与数据权限中心设计

## 目标

平台权限从“功能权限”升级为“功能权限 + 数据范围”，确保用户既能看到被授权的菜单，也只能访问所属项目组或标签范围内的资产。

## 身份与组织

- Keycloak 继续负责用户认证和单点登录。
- 网关通过系统管理接口同步 Keycloak 用户、用户组和 Realm Role。
- PostgreSQL 保存平台用户、平台角色、Keycloak 用户组映射、同步时间和状态。
- Keycloak 用户组或平台手工配置的项目组共同构成用户的数据范围。

## 数据范围模型

支持四种模式：

- `all`：全部资产。
- `groups`：项目组范围。
- `tags`：标签范围。
- `none`：无资产访问权限。

用户最终数据范围由用户个人配置和所属平台角色取并集；任一角色为 `all` 时，用户获得全局资产范围。

## 权限执行

- 用户登录后，认证服务通过访问策略解析器读取平台用户和角色。
- CMDB 列表、汇总、分析报表、资产详情、历史、导入、导出和监控目标接口按数据范围过滤。
- 资产新增时不能创建到无权限项目组。
- 资产编辑和导入不能读取或迁移无权限资产。
- 批量资产治理会逐台校验数据范围。
- 远程运维目标选项和解析结果按数据范围过滤。
- 治理规则等全局配置操作要求 `all` 数据范围。

## 系统管理

系统管理中心提供：

- 用户角色、状态、项目组和标签范围维护。
- 平台角色功能权限和数据范围维护。
- Keycloak 用户和组织一键同步。
- 同步结果、错误明细和审计记录。
- 模块配置、审计日志和平台参数查看。

## 运维配置

Gateway 使用以下环境变量连接 Keycloak Admin API：

- `KEYCLOAK_ADMIN_URL`
- `KEYCLOAK_ADMIN_USERNAME`
- `KEYCLOAK_ADMIN_PASSWORD`
- `KEYCLOAK_REALM`

密码来自 Kubernetes Secret，不写入代码仓库。
